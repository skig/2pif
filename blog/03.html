C23 - new features added to the good old C

C language development

C programming language is one of the most popular programming languages during the last decades. It is used in the wide range of systems: from embedded applications running on low-cost MCUs to the modern HPC clusters used for AI models training. Such a remarkably broad scope of uses is explained by several factors:

  • C is relatively low-level, it gives a developer a lot of control over memory management and code execution
  • A lot of fundamental legacy code is written in C
  • The language is quite stable. It doesn't change much over time which helps to keep backward compatibility and reuse existing code in the new projects.
  • The language is simple and straightforward. It allows to compile existing code on the new platforms easily

Nevertheless, C language keeps slowly changing. Its standard had four revisions in the past 30 years: C99, C11, C17 and C23. Despite its name, C23 standard was released in 2024. Now, in 2025, it is a good time to break down the changes made in the C23 standard in this blogpost.

C23 brought a lot of changes. Not all of them are implemented in the modern compilers. If you are willing to try out new C23 features and to compile examples from this blogpost, I would recommend to use GCC version 15 and newer, or LLVM Clang version 19 and newer.

Let's take a closer look at some of the major changes in C23.

bit-precise integer types

_BitInt(N) allows to define int variable of N-bit size where N can be up to BITINT_MAXWIDTH defined in . GCC 15, for example, has BITINT_MAXWIDTH=65535 which allows operating with quite large integers.

This feature might be useful when operating with modular arithmetics in cryptography, or implementing network protocol with field lengths of several bits.

Example of how _BitInt(N) can be used to implement N-bit counter:

unsigned _BitInt(2) counter;
for (int i = 0; i < 8; i++)
{
    /* prints 0 1 2 3 0 1 2 3 due to wrapping of 2-bit counter */
    printf("%u ", counter++);
}

#embed

Replaces `xxd -i` command and simplifies build system when you need to insert external file content to source code. It can be used when there is need to insert media (icons, sound etc) to the executable, or when processing some data which can be compiled-in during compilation.

Simple example of using the #embed to load text data:

const char settings_json[] =
{
    #embed "compile_time_settings.json"
};

int main(void)
{
    load_settings(settings_json);
    // ...
}

See a code snippet demonstrating how to parse .wav file #embed-ded into source code.

enums with fixed underlying types

Let's assume you have a library communicating using serialized protocol with the following message header type defined in <protocol.h> 
typedef struct __attribute__((packed))
{
    enum
    {
        _BROADCAST_MSG_TYPE,
        _UNICAST_MSG_TYPE,
    } msg_type;
    char msg_len;
} msg_header_pre_t;

This type definition looks correct and the intention is quite clear. The message header contains two fields: `msg_type` and `msg_len`. However, this type definition is ambiguous when it comes to the fields size. The second field has a length of 1 byte regardless of a compiler or platform because it uses char type. But the `msg_type` field length is not defined properly because enum type doesn't have any size guarantees. The standard only requires a compiler to use a type that can fit all the possible enum values. In practice when compiling with GCC the msg_header_pre_t size can be 2 (if --short-enums options is used), or 5. Unfortunately this imbiguilty makes usage of such a type for communication between different libraries complicated because they can be compiled with different flags, so the field sizes will be different and the communication will be broken.

C23 solves this issue by allowing a developer to specify explicitly an integer type used for the given enum field. This option was already availably in many C compilers as an extension, but adding this feature to a standard make code more portable and the language more reliable in general. Underlying type can be defined using the following syntax: 

enum : char
{
    _BROADCAST_MSG_TYPE,
    _UNICAST_MSG_TYPE,
} msg_type;

See full example of enums with underlying types here.

constexpr

Allows to calculate values of scalar objects during compile-time. Unlike C++ constexpr, the C constexpr can't be used to evaluate function values, it can only be used for variables.

auto and typeof

Allows to improve code maintainability by assigning types for related objects implicitly. In the following code snippet foo(), bar(), i and m have int type: 

int foo(void)
{
    return 10;
}

typeof(foo()) bar(void)
{
    auto i = foo();
    typeof(i) m = i / 2;
    return m;
}

A couple more things

Small code readability improvements:

  • #elifdef directive is equivalent to #else if defined()
  • #elifndef directive is equivalent to #else if !defined()
  • 0b00001111 syntax allows to define binary numbers
  • 4'294'967'296 syntax allows to split digits in a number

See a code snippet demonstrating constexpr, auto, typeof and other small things.

Summary

C23 brought many changes to the language.

Some of them standardized the practices that were already implemented in most of the modern compilers as extensions. As an example, underlying enum types, or binary integer constants were already available in GCC, but now they became part of the standard, which makes the code using these extensions more portable.

Other features are completely new. For example, #embed preprocessor directive. It simplifies certain use-cases and makes life of developers easier.

It is unclear, which of the changes will be widely adopted by modern compilers, which of the changes will be not understood and not used by developers, and what changes will reveal new problems and make life harder. Only time will tell. And while developers community slowly start using the new C23 features, the WG14 working group is already working on the next revision of standard - C2Y - which will bring even more changes.
